# Engine review, October 2026

A review of [chatbot-engine](https://github.com/rouzbeh-abadi/chatbot-engine)
for correctness bugs, security holes, data-loss risks and places where the
docs say something the code does not do. It was made on 10 October 2026
against release 0.1.26 (`66fd46c`), the version ChatFrom runs in production
(`engine-langgraph:0.1.26`). No engine code was changed. It is the companion
of ChatFrom's own review, `docs/review-2026-10.md` in ChatFrom
([rouzbeh-abadi/chatFrom#1](https://github.com/rouzbeh-abadi/chatFrom/pull/1)),
which covers the app and lists what this review means for it.

What ships to ChatFrom is the `engine-langgraph` image: `engine/src`
(`chatbot_engine`) plus the workflow agent in `examples/langgraph-agent`
(`docker/engine-with-plugins.Dockerfile`). Both were reviewed in full. The
demo backend and frontend (`examples/backend`, `examples/frontend`) are
published as images too, and adopters are told to copy them, so they were
reviewed as well; ChatFrom does not run them, and their findings are kept
apart.

## How the review was done

The shipped code was split into nine slices: the API surface and settings;
ingestion and storage; retrieval; the chat turn; MCP and tools; the workflow
agent; evaluation, tracing and logging; images, CI, docs and the contract
with ChatFrom; and the demo. Each slice reviewer read its code against the
engine's own docs (`README.md`, `DEPLOYMENT.md`, `docs/*.md`) and against
twelve claims ChatFrom's docs make about the engine, and confirmed each finding
with a test that fails on today's code, or with exact lines where a test
cannot reach.

Every finding then went to two independent verifiers: one re-ran the test
and traced the code path from a real caller; the other tried to refute it
(mitigated by the app, by ChatFrom's settings, by a later line, already
documented) and set its own severity. A completeness critic then read every
slice's coverage and the whole source tree and named eight gaps no slice had
covered: tool servers' redirects, provider routing, metric labels, the
`/extract` slots, billing on failure paths, what a stop or kill leaves of a
document, deletion end to end, and a full disk. A second round of targeted
reviewers took those, each with an adversarial verifier. It added INGEST-12
to INGEST-19, MCP-2, TURN-10, EVALTRACE-10 and EVALTRACE-11, and widened
INGEST-4, TURN-8 and WORKFLOW-8. The full-disk gap was still being verified
when this version was written, and is not in it. Finally the lead re-checked the High findings against
the code, re-timed the quadratic ones, re-ran every test from its final
location to make sure it fails at the same line for the same reason, and
checked every cited line.

The threat model, in ChatFrom's setting: one engine serves every owner, on a
private network, behind one API key that only the app holds. So isolation
between projects is a tenant boundary; strangers' text reaches the engine as
messages, files, tool results and Ask answers; and owners, who are strangers
to each other, choose their MCP servers, Langfuse keys, workflows and
splitting settings. One tenant taking the shared engine down is therefore
High, as is anything that sends one tenant's data to another.

Severity:

| Severity | Meaning |
| --- | --- |
| **High** | An outage one tenant (or one visitor) can cause, one tenant's data reaching another, a prompt-injection guard the docs promise that does not hold, or an unauthenticated resource exhaustion |
| **Medium** | Data kept after delete, a security property claimed and missing with limited impact, a correctness bug a user sees, authenticated exhaustion |
| **Low** | Edge cases, wrong status codes, docs that drifted, hardening |

## What to fix first

Several findings share a fix, so the order below is by change, not by
finding.

1. **Stop one stranger from taking the shared engine down.** Make the closer
   pattern linear (TURN-2). Give `/extract` a parse budget and a per-caller
   share of its slots (INGEST-12). Require a minimum step between chunks
   (INGEST-1). Cap what a tool server's answer may be (MCP-3). Bound the
   keyword index (RETRIEVAL-1). Give indexing its own semaphore (INGEST-5).
   Run pausing graphs with `durability="exit"` (WORKFLOW-4).
2. **Key Langfuse clients by the whole tracing config, and bound them.** One
   change closes EVALTRACE-1 (another tenant's traces) and EVALTRACE-2
   (threads that are never freed).
3. **Keep strangers' text out of the system role in workflows.** Render
   variables into the person's turn, framed and cleaned (TURN-1,
   WORKFLOW-2), and accept a spaced closer (TURN-6).
4. **Add a project purge and a pending record.** One route that removes a
   project's records, chunks, originals, pauses and checkpoints, and a
   record written before the original, close INGEST-4, INGEST-16 and
   WORKFLOW-5. Purge Chroma's log after it (INGEST-17).
5. **Stop following tool servers' redirects** (MCP-2): a few lines in
   `mcp/client.py`.
6. **Pass OpenRouter a `provider` object** (TURN-10). ChatFrom's DPA needs
   it.
7. **Count every model call, and say when usage is partial** (TURN-8).

## High

### TURN-2: One visitor's file freezes the shared engine for seconds on every turn

- **Category:** resource exhaustion, triggered by a stranger
- **Where:** `engine/src/chatbot_engine/untrusted.py:77-80` (`closing_tag`), `:84-86` (`framed`), called synchronously from `agent/client.py:338` (`file_frames`), `examples/langgraph-agent/langgraph_agent/workflow.py:164` (condition steps) and `agent/retriever.py:392` (extracts)
- **Evidence:** the pattern `[<＜][/…]\s*file(?=…)[^>＞]*[>＞]` scans to the end of the text for every `</file ` that has no `>` after it, then backtracks. Timed on the real `framed()`:

  | Text | Time |
  | --- | --- |
  | 7,500 characters | 0.06 s |
  | 15,000 characters | 0.23 s |
  | 30,000 characters | 0.95 s |
  | 60,000 characters | 3.98 s |

  Ordinary text of the same size takes under a millisecond. The call runs on the event loop of the engine's one uvicorn process.
- **Failure scenario:** on a chatbot that takes files, a visitor sends a `.txt` made of `</file ` repeated. ChatFrom keeps 30,000 characters per file and sends up to three files, 60,000 characters, with every later turn (`libs/chat-files.ts:34-37`). Each turn of that conversation then holds the engine's event loop for about two seconds, and longer with workflow condition steps. At the app's 40 messages a minute per address that is most of every minute. Every owner's chat stalls, deadlines cannot fire, and the health check can fail. The same cost applies to planted text in knowledge extracts.
- **Fix:** neutralise the opener alone, with no scan to `>`: `[<＜][/…]\s*file(?=[\s/>＞…]|$)` becomes `[/file]`. Or bound the tail, `[^<>＜＞\n]{0,64}[>＞]`. Cut a file to its limit before framing it (`file_frames`, `condition_prompt`), and add a timing test.
- **Confirmed by:** `engine/tests/review/test_turn.py` › `test_framing_a_file_of_unclosed_closers_takes_linear_time`: "one prompt took 2.11s of event-loop time (an ordinary one of the same size: 4.7ms)".
- **ChatFrom:** exposed on every chatbot with visitors' files on. No account is needed.

### INGEST-1: An overlap just under the chunk size multiplies a document about 100 times and runs the engine out of memory

- **Category:** resource exhaustion, by any owner
- **Where:**
  - `engine/src/chatbot_engine/rag/splitter.py:142`
  - `api/documents.py:48-49` and `models/documents.py:78-79` (the bounds)
  - `rag/vector_store.py:282` (one `aadd_documents` for every chunk)
- **Evidence:**
  - The only check relating the two settings is `overlap < size`. The bounds are 100 to 8,000 for the size and 0 to 2,000 for the overlap.
  - `index_max_chars` limits characters, not chunks.
  - Every vector of a document is held in memory before Chroma writes any: about 50 KB per 1,536-dimension vector.
  - Measured at size 100, overlap 99: CJK text becomes 99.9 times as many characters to embed, English prose 11 times.
- **Failure scenario:** a free-plan ChatFrom owner sets Length splitting to size 100, overlap 99, which the app accepts (ChatFrom's `libs/chunking.ts:20, 115` checks only overlap < size). They then upload a 200 KB Chinese text file. That is about 65,000 chunks and about 3.2 GB of vectors at once, in an engine limited to 3 GB. The engine is killed, and every chatbot is down while it restarts (86 seconds to 6 minutes, per the compose file). The owner can repeat it 30 times a minute. Embedding spend on ChatFrom's key grows by the same factor (app finding BILL-3).
- **Fix:**
  - Bound chunks per document (`ENGINE_INDEX_MAX_CHUNKS`) and refuse a document over it before embedding.
  - Require a minimum step, for example `overlap <= size / 2`.
  - Embed and write in batches, so memory stays flat whatever the count.
- **Confirmed by:** `engine/tests/review/test_ingest.py` › `test_overlap_cannot_multiply_a_documents_chunks_without_bound`: "5000 characters became 4901 chunks (~98x the document embedded)".
- **ChatFrom:** exposed. App-side, require the same minimum step in `checkChunking`.

### EVALTRACE-2: Every new Langfuse public key leaves four threads behind, so one owner can exhaust the engine's processes

- **Category:** resource exhaustion, by any owner
- **Where:**
  - `engine/src/chatbot_engine/tracing.py:36-38` and `:103-113`
  - The Langfuse SDK's `LangfuseResourceManager`, which keeps one instance per public key for the life of the process
- **Evidence:**
  - The engine bounds its own dictionary to 256 handlers (`_PER_PROJECT_MAX`).
  - Each `Langfuse(public_key=…)` for a new key still starts an exporter thread and two consumer threads, which the SDK never frees.
  - Measured: 120 distinct keys added 480 threads and 362 MB.
- **Failure scenario:** an owner saves tracing with public key `pk-1` (any secret, a host the app accepts as public https) and sends one turn, then repeats with `pk-2`, `pk-3` and so on. The app never checks the keys against Langfuse (`libs/engine/assistant-patch.ts:176-193`). After about 120 keys the engine reaches its `pids_limit: 512`. From then on new threads and processes fail across the engine for every tenant: anyio workers, extract subprocesses, Chroma. Nothing recovers until a restart.
- **Fix:**
  - When a handler is evicted, remove its key from the SDK's registry and shut the instance down.
  - Better, export every tenant's spans through one processor that picks credentials per span.
  - Cap how many new keys a caller may register per hour.
- **Confirmed by:** `engine/tests/review/test_evaltrace.py` › `test_per_assistant_langfuse_clients_are_bounded_by_the_cache_cap`: "9 Langfuse clients alive, 36 threads" with a cap of 3.
- **ChatFrom:** exposed. App-side, check a Langfuse key pair against its host when it is saved.

### EVALTRACE-1: A chatbot's traces go to whichever host was first sent with its public key, even by another tenant

Also reported as INFRA-1.

- **Category:** security (cross-tenant)
- **Where:**
  - `engine/src/chatbot_engine/tracing.py:92-113`
  - Langfuse 4.15.2 `resource_manager.py:137-138`: `if public_key in cls._instances: return cls._instances[public_key]`
- **Evidence:**
  - The handler is cached by public key alone, and so is the SDK's client. The first request that names a public key fixes its host and secret until the engine restarts.
  - A later request with the same key but its own host and secret is traced with the first one's.
  - The engine's eviction does not reach the SDK's registry.
- **Failure scenario:**
  1. After an engine restart (every ChatFrom deploy), owner B saves tracing with owner A's Langfuse public key, any secret, and B's own https host.
  2. B sends one turn before A's chatbot does.
  3. Until the next restart, every traced turn of A is exported to B's host: A's prompt, visitors' messages, extracts, tool calls and results.

  Langfuse treats public keys as publishable (its browser SDK puts them in page scripts), so the precondition is realistic. In the other order, B's traces land in A's project.
- **Fix:**
  - Bind a destination to (public key, host, secret).
  - When a request names a registered key with a different host or secret, trace nothing for that turn and log it without the key.
  - App-side, refuse a public key another owner already uses, and check the key pair against the host when it is saved.
- **Confirmed by:**

### RETRIEVAL-1: The keyword index has no memory bound, and simultaneous cold builds are not merged

### MCP-2: Tool servers' redirects are followed to any address, with the server's headers and the visitor's ids

- **Category:** security (egress)
- **Where:**
  - `engine/src/chatbot_engine/mcp/client.py:58-62`: the session's client comes from `create_mcp_http_client`.
  - `mcp/shared/_httpx_utils.py:79` in the MCP SDK (2.0.0, locked): `{"follow_redirects": True}`. Its docstring says "Always enables follow_redirects".
  - `models/chat.py:66`: a server's `url` is a bare `str`. Nothing in the engine checks an address, before or after a redirect.
- **Evidence:**
  - On a redirect to another origin, httpx drops only `Authorization` and `Cookie`. Every other header goes along: the server's own headers, `X-User-Id` and `X-Session-Id`.
  - A 307 sends the JSON-RPC body again, to the new address.
  - A 303 turns a tool call into a GET of any path and query the redirect names, for example `/admin/config?x=1`.
  - If the server redirects every request, the whole MCP session moves to the other address. The client keeps its first URL, so each request bounces again, and it adopts the session id the internal server issues. A tool on an internal MCP server runs, and its answer comes back into the turn.
  - From a service that is not an MCP server, nothing comes back: the tool error reads "unhandled errors in a TaskGroup". The body appears only in the engine log.
- **Failure scenario:** an owner saves an MCP server URL that passes the app's check: a public https host. At discovery or at a tool call, that server answers with a 307 to an address the app would refuse. The engine sends the call there, headers and visitor ids included. The app's address check (`reachableServers`) covers only the first hop. No rebinding race is needed, because any web host can send a redirect.
- **Fix:**
  - In `_session`, build the `httpx2.AsyncClient` with `follow_redirects=False`, with the same headers and timeout, and pass it to `streamable_http_client`. Treat a 3xx as a server error.
  - Better: an opt-in egress policy (for example `ENGINE_MCP_PUBLIC_ONLY`), enforced by a transport that checks the address it actually connects to. That also closes DNS rebinding between the app's check and the engine's call.
  - Say in `docs/backend-integration.md` that a caller's URL check needs this.
- **Confirmed by:** `engine/tests/review/test_mcp.py`:
  - `test_mcp2_a_redirect_to_an_inward_address_is_not_followed`: a 307 to the link-local metadata address is dialled.
  - `test_mcp2_a_servers_own_headers_never_follow_a_redirect_to_another_origin`: a 303 sends `X-User-Id` and `X-Api-Key` to another host over plain http.
  - `test_mcp_redirects.py` › `test_a_redirect_does_not_reach_an_internal_path[303]` and `[307]`, and `test_a_session_cannot_be_bounced_onto_an_internal_mcp_server`. That last test shows an internal tool's answer read back.
  - `test_mcp_redirects.py` › `test_a_non_mcp_internal_reply_is_not_read_back` passes: nothing comes back from a service that is not an MCP server.
- **Severity:** Medium in ChatFrom's setting, where what is left is blind GETs and POSTs from inside the private network. It is High for an adopter whose internal tool server trusts `X-User-Id`, the documented pattern. A verifier looked for something to reach inside ChatFrom and found nothing:
  - `app:3000` serves the routes the internet already reaches.
  - Every engine route except health needs the API key, which the MCP client never sends.
  - ChatFrom's own MCP server needs a per-chatbot token in its path, and the owner never learns it.
  - The only headers are the owner's own site token and its own visitors' ids.
- **ChatFrom:** exposed, as described above. `docs/security.md` covers a name that moves inward between the app's check and the engine's call, but not a redirect.

The engine answers 502, or the app gives up, while the provider finishes and bills the read (about $0.006 on gpt-4.1-mini). The app records nothing and tells the visitor to try again.
- **Fix:** stream the read with `stream_usage`, so a slow but live read ends with its bill. On a failure after sending, return an estimated usage marked as such. Qualify the docs.
- **Confirmed by:** `engine/tests/review/test_usage.py` › `test_an_image_read_that_timed_out_after_the_provider_started_says_what_it_spent`: "status 502 … with no usage at all". Two things were not checked offline: whether OpenRouter bills a non-streamed call whose caller went away, and whether it sends keep-alive bytes.
- **ChatFrom:** exposed narrowly. The app's 3 files a minute per visitor bounds it.

### INGEST-19: An index that fails after paid embedding batches reports nothing embedded

- **ChatFrom:** exposed, for negligible amounts (about $0.005 per 1,000 chunks). The engine reports no embedding spend by design. A verifier rated this close to no finding. It is kept for the app's billing model, next to the app review's BILL-3.

### TURN-8: A partial bill is reported as the turn's exact cost when a call is cut, retried or reports no usage

- **Where:**
  - `engine/src/chatbot_engine/agent/client.py:160-162`: `add_usage` returns for a reply with no usage before `calls` is counted at `:171`.
  - `client.py:1017-1043`: `stream_reply` sums each attempt afresh and drops a failed one at the `continue`.
  - `client.py:1087`: `price_usage` presents the summed bill as exact when `billed_calls == calls`.
  - `agent/router.py:119-122`; `api/streaming.py:59-60`: a turn cut by the deadline or an error reports the meter as it stands.
- **Evidence:** each case below reports `cost_usd` as OpenRouter's exact bill, though some of the spend is missing:
  - **Deadline.** The rewrite finished and the answer was streaming when the deadline passed: the usage event says 110 tokens.
  - **A stream that breaks after its first text** is not retried. The usage event carries only the rewrite's bill: 0.00004 against 0.00254 charged.
  - **A stream retried before its first text** (`ENGINE_PROVIDER_MAX_RETRIES`, 3 by default). The provider generated, and billed, the first attempt, but only the retry's bill is reported: 0.0017 against 0.0033 when the first attempt had sent its usage, and against 0.0029 when it broke while reasoning.
  - **A reply with no usage chunk** is not counted as a call. A follow-up turn reports only the rewrite. A one-call turn reports 0 tokens and a null cost, which ChatFrom prices as 0, and so bills 0 credits. An image read reports `{0, 0, null}`, and the app records it as free.
- **Fix:**
  - Count every call in `add_usage`, including one with no usage, so the cost falls back to `ENGINE_PRICING` or null rather than a partial exact bill.
  - Have `stream_reply` hand back what each failed attempt spent.
  - When a call was cut or reported nothing, mark the usage as partial or estimated (a `usage_complete` field), so the caller does not take it as billed.
- **Confirmed by:**
  - `engine/tests/review/test_turn.py` › `test_a_turn_stopped_mid_answer_does_not_report_the_rewrite_as_its_whole_spend`.
  - `test_usage.py` › `test_an_answer_stream_broken_after_its_first_text_does_not_report_the_rewrite_as_exact`, `test_a_retried_attempt_that_had_sent_its_bill_is_counted`, `test_a_retried_attempt_that_broke_while_reasoning_is_not_hidden_behind_an_exact_bill`, `test_a_reply_without_its_usage_chunk_does_not_leave_a_partial_bill_presented_as_exact`, `test_a_one_call_turn_without_its_usage_chunk_is_not_reported_as_zero_tokens` and `test_an_image_read_whose_reply_carried_no_usage_is_not_reported_as_free`.
  - `test_usage.py` › `test_an_attempt_refused_before_streaming_costs_nothing` passes: a retry after an outright refusal (503) does report the whole bill.
- **ChatFrom:** exposed, rarely, and for small amounts. The app takes any non-null `cost_usd` as billed (`libs/pricing.ts:176`) and estimates only when no usage comes at all (`libs/chat-turn.ts:333`), so the missing spend is absorbed by the platform. Nobody can trigger it on purpose: it needs a deadline, a broken stream, or a provider leaving usage out. Whether OpenRouter bills a stream cut part-way could not be checked offline.

### WORKFLOW-8: The checkpoint store's connection is never closed, so the engine waits for SIGKILL to stop

- **Where:**
  - `examples/langgraph-agent/langgraph_agent/pauses.py:76-94`; `engine/src/chatbot_engine/app.py:50-71`
  - `docker/engine-with-plugins.Dockerfile:48-50` and `engine/Dockerfile`: exec-form `CMD ["uvicorn", …]` with no init, so uvicorn is the container's PID 1.
- **Evidence:**
  - Any turn of a workflow with an Ask step opens the store, even a stale resume that calls no model. Its aiosqlite thread is not a daemon, and nothing closes it.
  - After SIGTERM, uvicorn shuts down gracefully, then re-raises the signal (`uvicorn/server.py:339-340`). As PID 1 the process ignores a signal it raises at its default action, and the interpreter then waits on the thread for ever.
- **Failure scenario:** after such a turn, every `docker stop` or redeploy logs "Application shutdown complete" and then hangs until Docker's SIGKILL at 10 s. That adds 10 s of engine downtime to every deploy. A script, or a server stopped with Ctrl-C, hangs at exit the same way, and this is the thread warning in the engine's own suite.
- **Fix:** `Pauses.close()`, called from the app's shutdown. Also run an init (`tini`, or `init: true` in compose), so signals reach uvicorn with their usual meaning.
- **Confirmed by:**
  - `engine/tests/review/test_workflow.py` › `test_a_process_that_paused_a_turn_can_exit`: "the process did not exit within 30 s".
  - `test_index_crashes.py` › `test_the_engine_as_pid_1_exits_on_sigterm_with_nothing_in_flight[pause_store_opened]`: "still running 10.0s after SIGTERM with nothing in flight". The `[no_pause_store]` control passes, and a verifier saw the same run exit outside a PID namespace, so PID 1's signal rules are the cause.
- **ChatFrom:** exposed. Its compose file sets no `init` and no `stop_grace_period` for the engine. That uvicorn is PID 1 in the base image was inferred from the exec-form `CMD`; the registry could not be reached to confirm it.

| 12 | The usage the engine reports is complete and correct (the app bills on it) | **Partly** | Every finished call that reports usage is counted. A call cut by the deadline, a stream that broke or was retried, and a reply with no usage leave a partial bill presented as exact (TURN-8). An image read that runs past 45 s reports nothing (INGEST-18), nor does the embedding of a failed index (INGEST-19). The per-turn query embeddings are not counted, as documented |

Four questions the app review left open are settled:

- **Unknown engine events reaching visitors.** The engine emits a closed set
  of eight event types, every line a validated model. No unknown event
  reaches the app's filter.
- **Lone surrogates in history.** The engine neither repairs nor cleanly
  refuses them (API-4). The app's own cut is what must not make them.
- **The checkpointer and deletion.** It keeps Ask answers after the app
  deletes a conversation or a chatbot, and offers no way to delete them
  (WORKFLOW-5).
- **Image reads being free.** A read whose reply carries usage is billed
  correctly. One whose reply carries none is reported as free (TURN-8), and
  one the provider is still writing after 45 s reports nothing (INGEST-18).

## Worth a look (not confirmed)

Seen, but not confirmed offline, or too small to rate:

- **Framing.**
  - Default-ignorable characters outside `visible()`'s list (U+00AD, U+034F, U+180B–U+180F, U+FFF9–U+FFFB, more of the tag block) are kept. They cannot spell text, but they can split a closer (`</ext­racts>`) or dodge a warning.
  - An HTML-entity closer (`&lt;/extracts&gt;`) is not neutralised.
  - The closer pattern's `[^>]*` also replaces legitimate text: a file that mentions `</file` and has a `>` many lines later loses everything between.
  - Whether a model reads any of these as the end of a frame was not tested.
- **MCP servers.**
  - Per-server header names may be `Host`, `Content-Length`, `Transfer-Encoding` or `Mcp-Session-Id`.
  - Duplicate server names, and a tool allowed on two servers, are accepted, so a call can go to a server that does not allow it. The app refuses both.
  - `mcp_servers` has no maximum, and discovery is sequential.
  - The app and the engine resolve a tool server's name separately, so a name that rebinds between the two reaches inside. This follows from the code (MCP-2's connect-time check closes it) but was not tested.
- **Settings and limits.**
  - An `ENGINE_API_KEY` with a non-ASCII character can never match (the header is decoded as latin-1, the key compared as UTF-8), and the engine starts without a warning.
  - A rate-limit token is charged even when the body then fails validation.
- **Retrieval.**
  - Hits are merged by text, so a page crawled under two URLs fills candidate slots and leaves fewer distinct extracts.
  - `collection_name` folds `a/b` and `a-b` into one collection.
- **Workflows.**
  - Two `Pauses` objects (the chat and judge routers) open one SQLite file with separate locks.
  - A deadline that falls between recording a pause and sending its event keeps a pause the visitor never got.
  - A condition step takes the first label that appears anywhere in a wordy answer ("not refund, other" → refund).
  - Email and url answers may carry control characters into tool arguments.
  - A step prompt can name one variable 400 times, making a system message of millions of characters (owner only).
- **Evaluation.**
  - A judge model that ignores the JSON schema would fail every batch.
  - Duplicate case ids are accepted and shown under each other.
  - Evaluation spend is missing from `/metrics`.
- **Chat files under load.** The 2 to 2.9 times slowdown while two crafted PDFs are read (INGEST-12) was measured with the process pinned to one or two CPUs, not in the 1.5-CPU container.
- **`/health/ready`** has no auth and runs a synchronous Chroma heartbeat and an entry-point scan on the event loop. ChatFrom calls it when the dashboard renders.
- **The demo.**
  - The CSV export does not neutralise formulas (`=`, `+`, `-`, `@`).
  - Error events show the engine's internal address.
  - The admin's `WRITE_TOOLS` omits `remember`.
  - Memory's 64-character id columns would refuse longer session ids on Postgres.

## Checked and found sound

So the next review can skip them unless the code changes. Where a passing test
in `engine/tests/review/` holds one, it is named.

- **Authentication.**
  - The API key is compared in constant time over every configured key, and the key is never logged.
  - Production refuses to start without one; an empty value counts as none (`test_an_empty_key_in_production_does_not_open_the_engine`).
  - Production hides `/docs`, `/redoc` and `/openapi.json` and puts `/metrics` behind the key.
  - There is no CORS middleware.
- **Rate limits** are keyed by the authenticated key's name, never by a client address, so `X-Forwarded-For` cannot pick a bucket (`test_a_forwarded_for_header_does_not_choose_the_rate_limit_bucket`).
- **Request validation.**
  - Unknown JSON fields are refused at every nesting level (`test_production_refuses_unknown_json_fields_at_every_level`).
  - JSON bodies are capped by `Content-Length` and while streaming.
  - A 401 log line cannot be forged with CR/LF (`test_a_refused_path_cannot_write_a_second_log_line`).
- **A reader that disconnects stops the turn** through both middlewares (`test_a_reader_that_goes_away_stops_the_turn`), so the app's Stop ends the provider's billing.
- **Events are a closed set** of eight types, each a validated model. Any failure becomes `error` then `done`.
- **Isolation between projects.**
  - Vector search always filters by project.
  - The keyword index is built per (collection, exact project id).
  - Deletes and re-indexes check the registry by (project, document) and filter chunks by both.
  - There is no path traversal (blob keys are 32-hex document ids) and no SQL injection (bound parameters throughout).
  - In a shared collection of 30,000 chunks, a 12-chunk project got all of its own chunks and no others.
- **An update embeds before it removes old chunks**, so a provider failure leaves the old version answering. All chunks are embedded before one write, so a failure part-way never mixes versions.
- **Re-index never writes the original**, so a failed or killed re-index leaves it as it was. A caller that gives up does not cancel an upload: it finishes.
- **A delete of a listed document is complete.** Its record, its chunks in Chroma's live tables and its original all go. SQLite's `secure_delete` is on in the image's library, so freed pages keep no copy (but see INGEST-17 for Chroma's write log). The engine runs one process, so a delete's keyword-index invalidation reaches every reader.
- **PDF reading is bounded**: a spawned process killed at its deadline, with CPU and memory limits, lowered inflate caps and a character limit.
- **Framing.**
  - In the loop agent, extracts and files travel in the person's turn.
  - The common closer spellings are neutralised (any case, `</ x >`, fullwidth brackets, look-alike slashes), and header lines that look like `[n]` are escaped.
  - `visible()` removes every category the docs list and keeps the joiners and direction marks.
- **Tools.**
  - The allowlist is exact at listing and at call time: a name differing in case, prefix or suffix is never sent (`test_sound_a_name_that_differs_from_the_allowlist_never_reaches_the_server`).
  - One server's headers never reach another (`test_sound_one_servers_headers_never_reach_another_server`).
  - A server that never answers is stopped at the deadline (`test_sound_a_tool_server_that_never_answers_is_stopped_at_the_deadline`).
  - Server-initiated sampling and elicitation are refused.
  - A redirect cannot add tools: the allowlist is applied to what discovery returns and again at call time. Per-server headers refuse CR, LF, NUL and the engine's own header names.
  - What a service that is not an MCP server answers to a redirected call does not come back to the turn (`test_a_non_mcp_internal_reply_is_not_read_back`); see MCP-2 for one that is.
- **Evaluations run no tools** on any path: `/judge` with the loop, graph and workflow agents, and `/eval/rag` (`test_sound_an_evaluation_runs_no_tool_on_the_server`, `test_sound_a_workflows_tool_step_and_hand_off_run_nothing_under_the_judge`). The judge's transcript is in the human turn.
- **Usage.**
  - Usage is summed across tool rounds, the rewrite and the rerank without double counting.
  - Stream retries happen only before the first text and never repeat a tool call.
  - A failed turn reports its meter.
  - A retry after an outright refusal reports the whole bill (`test_an_attempt_refused_before_streaming_costs_nothing`).
  - The engine never switches model within a turn and sends OpenRouter no `models` fallback list (`test_the_engine_never_switches_model_within_a_turn`).
- **The workflow agent.**
  - A resume is claimed atomically and only in the same chatbot, conversation and workflow (by hash).
  - It expires after its TTL on resume.
  - A finished or stopped turn forgets its state.
  - `render()` is single-pass (no template injection).
  - Phone, url and choice answers are checked.
- **Tracing.**
  - User ids are pseudonymised with an HMAC keyed on the API keys.
  - With tracing off, no callbacks run.
  - Langfuse's span processor sends a span only to the client of its own public key (but see EVALTRACE-1 for which client that is).
- **The release workflow**: actions pinned by commit, `contents: read` by default, and the tag passed as a variable. Images run as uid 10001 with `/app` read-only.
- **The app↔engine contract.**
  - ChatFrom's `tests/fixtures/engine-schemas.json` matches the 0.1.26 models exactly.
  - Its request types use only declared fields, and its event union covers all eight events.
  - Every `ENGINE_*` name in the docs is a real setting, with the documented default.

## Tests to add

The tests in `engine/tests/review/` already hold each confirmed finding;
each becomes a plain test when its fix lands. What follows is coverage the
suite still lacks.

### Unit and API tests (pytest, every push)

- **Auth before the body.** For every protected route, a call without
  `X-API-Key` gets 401 having read no body bytes. Do it for JSON, multipart
  and urlencoded bodies, counting `receive()` bytes as the review's ASGI
  harness does. Add a route inventory that fails when a router is mounted
  outside the protected one.
- **Every model input of a turn.** For the loop, graph and workflow agents,
  collect every message list each model call receives: the answer, rewrite,
  rerank, condition, Ask reading and reply-to calls. Assert that:
  - no system message holds a substring of a tool result, Ask answer, file,
    extract or the visitor's message;
  - no input holds a character `visible()` would remove.

  This one test would have caught TURN-1, TURN-4 and WORKFLOW-2.
- **Linear time.** `framed()`, `file_frames()`, `instruction_warnings()`,
  the splitter and `tokenize()` on crafted inputs at 16 KB and 128 KB,
  asserting the ratio of the times, not a time.
- **Bounded memory.** Under `tracemalloc`:
  - indexing a 2 M-character document at chunk size 100 and overlap 99;
  - a keyword index over 10 MB of text;
  - a 50 MB MCP result;
  - a paused workflow with a 5 MB tool result.

  Each against a fixed budget.
- **422 hygiene.** No 422 body contains `input`. A lone surrogate anywhere
  (message, history, attachments, `system_prompt`, header values,
  `resume.value`) gives a clean 422 or is repaired, never a 500.
- **Caches keyed on everything that matters.** Two configs differing only
  in server name, header values, Langfuse host or secret, or embedding model
  never share a tool list, a tracing client or a vector-store wrapper.
- **Usage.** A deadline mid-answer, a provider error after text, a retried
  stream, and a reply with no usage chunk each report either no usage, or
  usage marked as partial.
- **Metrics.** A tool name the turn does not have is counted under one fixed
  label, never its own.
- **Chat-file reads.** One caller cannot hold every `/extract` slot, and a
  multi-page PDF with no text is refused for its parse budget well before
  the deadline.
